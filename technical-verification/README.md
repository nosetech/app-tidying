# Technical Verification Scripts - 技術検証スクリプト集

このディレクトリには、macOSのウィンドウ管理機能に関する技術検証スクリプトが含まれています。App Tidying プロジェクトの実装可能性調査や機能検証に使用されます。

## スクリプト一覧

### 1. `move_to_external_display.sh`

**目的**: 指定したアプリケーションを外部ディスプレイの中央に移動させる

**機能**:
- 引数で指定されたアプリケーション名を受け取る
- アプリケーションの起動状態を確認（起動していなければ起動する）
- ウィンドウが表示されるまで最大10秒待機
- 外部ディスプレイの座標情報を取得（Finder経由）
- AppleScriptでウィンドウのサイズと位置を設定

**使用例**:
```bash
./move_to_external_display.sh "Google Chrome"
./move_to_external_display.sh "Finder"
```

**技術詳細**:
- 外部ディスプレイの座標: `左上: (-560, -1440)`, サイズ: `2560x1440`（ハードコード値）
- ウィンドウ待機時間: 最大10秒（1秒ごとにウィンドウ数をチェック）
- AppleScript経由でウィンドウ操作を実行

### 2. `detect_stdout.sh`

**目的**: 標準出力が利用可能かどうかを判定し、実行環境に応じて出力方法を切り替える

**機能**:
- TTY（端末）が接続されているかをチェック（`-t 1`）
- `$TERM` 環境変数の有無を確認
- ターミナル実行時は標準出力に出力
- ターミナル外実行時（Automator等）はダイアログで表示

**判定ロジック**:
1. TTY接続: `if [ -t 1 ]` - 標準出力利用可能
2. TERM環境変数: `if [ -n "$TERM" ]` - 標準出力利用可能
3. その他: ダイアログ表示（標準出力利用不可）

**使用例**:
```bash
./detect_stdout.sh
```

**応用例（logger.rsでの実装）**:
```rust
fn is_running_in_terminal() -> bool {
    std::env::var("TERM").is_ok()
}
```

**テスト項目**:
1. **テスト1**: ターミナルでの通常実行（標準出力利用可能）
2. **テスト2**: パイプ経由での実行（標準出力利用不可をシミュレート）
3. **テスト3**: ファイルへのリダイレクト（標準出力利用不可をシミュレート）
4. **テスト4**: stdoutが閉じられている状態
5. **テスト5**: TERM環境変数が未設定の環境

**使用例**:
```bash
./test_stdout_detection.sh
```

**実行環境シミュレーション**:
- `bash script.sh 2>&1 | cat` - パイプ環境テスト
- `bash script.sh > /tmp/file` - リダイレクト環境テスト
- `TERM="" bash script.sh` - 環境変数空の環境テスト

### 4. `get_display_info.sh`

**目的**: macOSのディスプレイ情報を詳細に取得する

**取得情報**:
- **JXA（JavaScript for Automation）経由**:
  - ディスプレイ名（ローカライズされた名前）
  - 物理解像度（ピクセル数）
  - UI解像度（論理解像度）
  - スケーリング係数（Retinaディスプレイ判定）
  - メインディスプレイの判定

- **AppleScript経由**:
  - 全体の画面境界座標（左, 上, 右, 下）

**技術詳細**:
- NSScreen フレームワークでディスプレイ情報取得
- `backingScaleFactor` でRetinaディスプレイのスケーリング係数を取得
- `localizedName` でシステム言語に対応したディスプレイ名を取得

**使用例**:
```bash
./get_display_info.sh
```

**出力例**:
```
ディスプレイ 0: Built-in （メイン）
  物理解像度: 2560x1600
  UI解像度: 1280x800
  スケール係数: 2.0x
```

### 5. `get_window_info.sh`

**目的**: 実行中のアプリケーションのウィンドウ情報を取得し、各ウィンドウがどのディスプレイに位置しているかを判定する

**機能**:
- システム設定ファイルからディスプレイ配置情報を取得（`windowserver.displays.plist`）
- Python3で plistlib を使用してディスプレイ設定をパース
- JXAでディスプレイ名を取得
- AppleScriptで各アプリケーションのウィンドウ情報を取得
- ウィンドウの位置からディスプレイを判定

**ウィンドウ-ディスプレイ判定アルゴリズム**:
1. **中心座標判定**: ウィンドウ中心がディスプレイ内に含まれるかチェック
2. **重なり面積判定**: 複数ディスプレイに跨る場合、最大重なり面積のディスプレイを選択
3. **最近接ディスプレイ判定**: どのディスプレイとも重ならない場合、最も近いディスプレイを選択

**使用例**:
```bash
./get_window_info.sh
```

**出力形式**:
```
Google Chrome | Development | 0,25 | 1440x900 | Built-in
Safari | Homepage | 1920,100 | 1024x768 | External Display
```

**技術詳細**:
- AABB衝突判定（軸並行境界ボックス）でウィンドウ-ディスプレイの重なりを判定
- ディスプレイ座標は `OriginX, OriginY, Wide, High` で定義

### 6. `verify_spaces.sh`

**目的**: macOSの仮想デスクトップ（スペース）機能に関する技術的な制約と可能性を検証

**検証項目**:
1. **スペース情報取得**: ✓ 可能
   - `com.apple.spaces.plist` から全スペース情報を取得可能
   - スペース数、スペース名、ウィンドウ割り当て情報を取得可能

2. **スペース総数取得**: ✓ 可能
   - Management Data から Monitor ごとのスペース数を集計

3. **スペース名取得**: ✓ 可能
   - Space Properties から name 属性を取得

4. **各スペースのウィンドウ情報**: ✓ 可能（ID形式）
   - ウィンドウID のみ取得可能
   - アプリケーション名との対応付けには追加分析が必要

5. **スペース作成/削除**: △ 手動のみ
   - AppleScript による自動化は不可（非公開API）

6. **スペース間のウィンドウ移動**: △ 困難
   - AppleScript での実装は非常に限定的
   - アクセシビリティAPI の許可が必須

**結論**:
- ✓ 情報取得は Python + plistlib で可能
- △ 操作の大部分は非公開API に依存し実装困難
- 将来的な公開API 拡張に期待

**使用例**:
```bash
./verify_spaces.sh
```

### 7. `verify_stage_manager.sh`

**目的**: macOS 13 Ventura以降のステージマネージャ機能の状態と、ウィンドウ操作への影響を検証

**検証内容**:
- macOSのシステム情報取得
- ステージマネージャの有効/無効状態確認
- `com.apple.WindowManager` の設定キー探索
- AppleScript、JXA、defaults コマンドでのステージマネージャ検出
- ウィンドウアクセスの動作検証
- Mission Control の設定確認

**発見事項**:
- AppleScript での直接的なステージマネージャ操作は不可
- 検査可能: ウィンドウの取得、位置・サイズの取得（ただし不正確な可能性あり）
- ステージマネージャが有効な場合:
  - アクティブなグループ内のウィンドウのみ完全にアクセス可能
  - バックグラウンドグループのウィンドウは不完全または不正な位置・サイズデータを返す可能性
  - ウィンドウレイアウト復元が正常に機能しない可能性

**使用例**:
```bash
./verify_stage_manager.sh
```

### 8. `verify_stage_manager_detailed.sh`

**目的**: ステージマネージャの詳細な状態確認と、有効/無効がウィンドウ操作に与える具体的な影響を検証

**確認項目**:
- macOSバージョン取得
- ステージマネージャの有効状態確認（`defaults read com.apple.WindowManager GloballyEnabled`）
- `com.apple.WindowManager` の全キー表示
- ウィンドウ取得テスト（有効時の動作検証）
- ステージマネージャグループ情報（WindowServer管理）
- ウィンドウアクセスの制限事項

**制限事項（ステージマネージャ有効時）**:
1. **ウィンドウアクセスの制限**:
   - アクティブグループ内のウィンドウのみ完全にアクセス可能
   - バックグラウンドグループは不完全なデータを返す可能性

2. **ウィンドウの位置・サイズへの影響**:
   - グループ相対座標での表現（画面座標では表現されない可能性）
   - 実際の表示サイズとの乖離

3. **複数アプリのグループ化**:
   - 複数アプリが1つのステージマネージャグループに属する可能性
   - グループ化解除はAppleScriptではサポートされない

4. **実装上の推奨事項**:
   - ウィンドウ操作前にステージマネージャ状態をチェック
   - 有効な場合の警告表示をユーザーに提供
   - 一時的な無効化の検討

**使用例**:
```bash
./verify_stage_manager_detailed.sh
```

### 9. `open_new_window.sh`

**目的**: AppleScriptを使用して、指定したアプリケーションの新規ウィンドウをメニュー操作で開く

**対応アプリケーション**:
- Finder
- Safari
- Google Chrome

**機能**:
- アプリケーション名を引数で指定
- アプリケーション起動状態をチェック（起動していなければ起動）
- AppleScriptでメニューバーにアクセス
- File / ファイル メニューを検索
- 「New Window」「新規ウィンドウ」メニューアイテムをクリック

**メニュー検索ロジック**:
1. メニューバーを取得: `menu bar 1`
2. ファイルメニューを検索: "File" または "ファイル"

4. 「New Window」または「新規ウィンドウ」を含むアイテムをクリック

**使用例**:
```bash
./open_new_window.sh Finder
./open_new_window.sh Safari
./open_new_window.sh Chrome
```

**出力例**:

### 10. `verify_new_window_menu.sh`

**目的**: AppleScriptでのメニューアイテム検索・実行機能の包括的な検証と実装例を提供

**検証テスト**:
1. **テスト1**: AppleScriptでメニュー構造へのアクセス可能性
2. **テスト2**: File メニュー内のメニューアイテム列挙
3. **テスト3**: Safari でのメニュー検索
4. **テスト4**: 汎用的な新規ウィンドウ実装例の表示
5. **テスト5**: Chrome での多言語メニュー検索テスト

**検証結果（全て ✓ 可能）**:
- AppleScriptでメニュー構造にアクセス可能
- 「New Window」「新規ウィンドウ」などの動的検索が可能
- メニューアイテムのクリック/実行が可能
- 複数アプリケーション（Finder、Safari、Chrome）で動作可能

**実装上の注意点**:
- **多言語対応**: メニュー名が言語設定によって異なる
  - 英語: "File", "New Window"
  - 日本語: "ファイル", "新規ウィンドウ"
- **エラーハンドリング**: メニューが存在しないアプリケーションもある
- **Accessibility API の許可**: UI要素へのアクセスには許可が必須
- **アプリケーション固有の対応**: メニュー項目がアプリごとに異なる

**使用例**:
```bash
./verify_new_window_menu.sh
```

**実装例（AppleScript）**:
```applescript
on openNewWindow(appName)
    tell application "System Events"
        tell process appName
            activate
            set menubar to menu bar 1
            set fileMenu to (first menu of menubar whose name is "File")

            repeat with mi in (every menu item of fileMenu)
                if name of mi contains "New Window" then
                    click mi
                    return "Success"
                end if
            end repeat
        end tell
    end tell
end openNewWindow
```

### 11. `verify_window_menu_control.sh`

**目的**: アプリケーション標準メニューバーの「ウインドウ」メニューにある「移動とサイズ変更」（OS標準のウィンドウタイリング機能）と「[ディスプレイ名]に移動」（ディスプレイ間移動機能）を、`osascript` 経由でコントロール（メニュー項目の検索・実行）できるかを検証する（Issue #116）

**背景**:
既存の `move_to_external_display.sh` は `position` / `size` プロパティを直接設定してウィンドウを移動・リサイズしている。本検証は、macOS標準の「ウインドウ」メニューに用意されているタイリング機能・ディスプレイ移動機能を、メニュー操作経由で利用できるかを確認するもの。

**検証対象**: Finder、Safari、Google Chrome（macOS 26.5.2、内蔵ディスプレイ + 外部ディスプレイの2画面構成で検証）

**検証結果**:

1. **「ウインドウ」メニューへのアクセス**: ✓ 可能
   - `System Events` 経由で `menu bar 1` の中から「ウインドウ」メニューを取得可能
   - **重要**: メニュー名の表記がアプリによって異なる
     - Finder / Safari: 「ウインドウ」（長音符なし）
     - Google Chrome: 「ウィンドウ」（長音符あり）
     - 実装時は両方の表記（および英語環境の "Window"）を候補として探索する必要がある

2. **「移動とサイズ変更」サブメニュー（OS標準タイリング機能）**: ✓ 可能
   - Finder / Safari / Google Chrome いずれも「移動とサイズ変更」メニュー項目を持つ
   - サブメニューには「左」「右」「上」「下」「4分割」「配置」（左と右、左と4分割 など）「前のサイズに戻す」等の項目がある
   - `click menu item "左" of (menu 1 of menu item "移動とサイズ変更" of ...)` で実際にウィンドウが左半分にタイル配置されることを確認済み（クリック前後で `position` / `size` の変化を検証）
   - Safari・Chromeで実機確認済み（Finderはウィンドウを閉じていたため位置検証はスキップされたが、メニュー構造自体は取得できている）

3. **「[ディスプレイ名]に移動」メニュー項目（ディスプレイ間移動機能）**: ✓ 可能
   - Safari・Chromeの「ウインドウ」メニューには、接続中の**他のディスプレイ名で動的に生成される**メニュー項目（例:「SDM27U9M2*30に移動」）が存在する
   - ウィンドウが外部ディスプレイに移動すると、項目名は「内蔵Retinaディスプレイに移動」に自動的に切り替わる（＝現在表示中でないディスプレイへの移動項目のみが表示される）
   - `click menu item` でクリックすると、実際にウィンドウが指定ディスプレイの座標空間へ移動することを確認済み（クリック前後の `position` の変化で検証）
   - ディスプレイ名は環境依存で動的に変わるため、固定文字列ではなく「〜に移動」で終わるメニュー項目を部分一致検索する実装が必要（「タブを新しいウインドウに移動」等、無関係な項目を除外する条件も必要）
   - **Finderは検証時にこのメニュー項目の状態が不安定だった**（ウィンドウが内蔵ディスプレイ上にあるにもかかわらず「内蔵Retinaディスプレイに移動」と表示される事象を観測）。Finderは特殊なシステムアプリのため、他アプリと同様の信頼性は保証できない可能性がある

4. **「画面全体に表示」（Issue #118 実装時に追加検証）**: ⚠️ 新しいSpaceへの切り替えを伴う
   - 「ウインドウ」メニュー直下の「画面全体に表示」をクリックすると、ウィンドウが画面いっぱいに拡大されるだけでなく、**実際のmacOSネイティブFullscreen機能（新しい仮想デスクトップ/Spaceへの切り替え）が発動する**ことを実機確認した
   - クリック後、Dockや他のウィンドウ・壁紙が見えなくなり、`System Events` で `value of attribute "AXFullScreen" of window 1` が `true` を返すことを確認
   - フルスクリーン解除には `click menu item` の再クリックでは効かず、`set value of attribute "AXFullScreen" of window 1 to false` （または実際のUI操作）が必要
   - `apptidying` プロジェクトは CLAUDE.md で「複数Spaceの管理: 実装予定なし」「表示中のSpaceのみサポート」と明記しているが、`"max"`（幅・高さともに`max`）指定時にこの挙動を採用することは Issue #118 で承認済み。ユーザーが `apptidying load` を実行するたびに新しい/既存のSpaceへ切り替わる可能性がある点は仕様として許容する

5. **「ディスプレイ移動」の代替手段（フルスクリーンボタンの長押しポップオーバー）**: △ 非推奨
   - ウィンドウ左上のフルスクリーンボタン（緑ボタン）を長押しすると表示される discoverability ポップオーバーには `AXShowMenu` アクションでアクセスできるが、これは通常の `menu` 属性の子要素として取得できない特殊なシステムUI
   - `perform action "AXShowMenu"` を実行すると、後続のAppleScript呼び出しで `AppleEvent がタイムアウトしました (-1712)` エラーが発生するケースを確認した（ポップオーバー表示中に別プロセスへの `activate` を送るとフリーズしうる）
   - この経路は不安定でハングのリスクがあるため、**メニューバーの「ウインドウ」メニュー経由（上記2・3）を採用すべき**であり、フルスクリーンボタンのポップオーバー経由は推奨しない

**実装上の注意点**:

- **メニュー名の表記揺れ**: 「ウインドウ」/「ウィンドウ」/ "Window" を候補として探索する
- **ディスプレイ名の動的検索**: 「[ディスプレイ名]に移動」は固定文字列ではなく、「に移動」で終わる項目をパターンマッチで検索する
- **Accessibility API の許可が必須**: 既存のUI操作系検証と同様
- **Finderは挙動が不安定**: メニュー構造は取得できるが、ディスプレイ移動メニューの状態表示に他アプリと異なる挙動が見られたため、Finderへの適用は追加検証を推奨
- **既存の直接プロパティ設定方式との比較**: メニュー操作は「半分」「4分割」等のOS標準の決められた配置しか選べないため、任意のピクセル座標を指定する現行の `layout.json` の仕様（`left`/`right`/`half`/`third` などのパターン指定・絶対座標指定の両方）を実現するには、引き続き `position` / `size` プロパティの直接設定方式が必要。メニュー操作はディスプレイ間移動の代替手段として有用

**使用例**:
```bash
./verify_window_menu_control.sh
```

**今後の実装への反映**:
- ディスプレイ間移動については、直接 `position` を計算して移動させる既存方式に加えて、メニュー操作という代替手段があることが分かった。ただし既存方式で座標計算は可能なため、`apptidying` 本体の実装では引き続き直接プロパティ設定方式を採用し、メニュー操作方式の採用は見送る（座標指定の柔軟性を優先）
- 採用を検討する場合は、Finderでの追加検証と、メニュー名の表記揺れ・多言語対応のテストケース拡充を別issueで行う

## 技術的な制約と今後の課題

### 実装可能な機能
- ✓ ウィンドウ情報の取得（位置、サイズ、タイトル）
- ✓ ウィンドウの移動・リサイズ
- ✓ アプリケーションの起動・活性化
- ✓ ディスプレイ情報の取得
- ✓ 新規ウィンドウの開き方（メニュー経由）
- ✓ 「ウインドウ」メニュー経由でのタイリング配置・ディスプレイ間移動（メニュー名の表記揺れ・動的検索への対応が必要）

### 実装困難な機能
- △ スペース（仮想デスクトップ）の作成・削除・移動
- △ ステージマネージャ設定の制御
- △ ウィンドウの正確な位置・サイズ検出（ステージマネージャ有効時）
- △ フルスクリーンボタン長押しのポップオーバー経由でのディスプレイ移動（ハングのリスクがあり非推奨）
